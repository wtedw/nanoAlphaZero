# MuZero research log

## Design and sources

Read the original [MuZero paper](https://arxiv.org/html/1911.08265v2),
especially appendices A, F and G, and DeepMind author Julian Schrittwieser's
[pseudocode](https://gist.github.com/Mononofu/6c2d27ea1b3a9b3c1a293ebabed062ed).
The baseline learns representation, action-conditioned dynamics, reward, policy
and value jointly. There is no observation reconstruction. Internal actions
are unmasked; only real roots receive simulator legality. Terminal continuations
learn absorbing targets without a terminal oracle in search. These follow
original MuZero. Its original board-game experiments omitted the reward loss;
this project deliberately retains it to exercise learned reward backups.

The production two-rung Gumbel search is a later search design, retained as
requested, not the original paper's sequential UCB search. Neural depth,
two-rung depth, expansion budget (R+S), and training unroll K are independent.
The initial network is a small residual MLP with a vector latent, not the
paper's large convolutional architecture. Reanalysis, reconstruction, consistency
losses, stochastic dynamics, and other extensions are absent.

## Targets and boundaries

`reward[t]` is the simulator reward resulting from `action[t]`, indexed by
the actor at t. `value[t]` is the subsequent discounted return for that actor.
Each real transition records the observed player change; the return scan uses
a negative discount when the next player differs. All 16 production environments
are deterministic alternating two-player zero-sum games with bounded rewards.
Latent search consequently uses discount -gamma. Its lower-level function also
allows a positive discount, but arbitrary multiplayer or irregular-turn games
are not claimed compatible.

An episode slot contains all observations, actions, intermediate rewards,
search policies, lengths, terminal flag and boundary bootstrap. Flashbax stores
and samples complete episodes; each unroll starts uniformly at a real position
in a sampled game. No sample crosses episode boundaries or buffer wraparound.
On terminal tails, value and subsequent reward targets are zero, actions are
random, and policy loss is masked. At a truncation boundary, the frozen model's
observed boundary value is bootstrapped; subsequent invented data are masked.
The initial reward head has no target. No human data or solver targets enter replay.

Latents use per-example min-max normalization with an epsilon denominator.
Gradients entering each dynamics call are scaled by 0.5. Each head's loss is
averaged over its valid batch/unroll entries; this is an explicit choice that
differs from a fixed 1/K divisor when masks differ. Value and reward use tanh
scalar regression; policy uses unmasked full-action cross entropy so unavailable
actions can be learned. Search policies themselves are root-masked.

Whole fixed-length episode batches simplify boundary correctness but waste
compute on finished games. Float observations and dense policies also make
this replay unsuitable for large chess production-scale batches without further
memory work. The implementation does not reuse production's outcome-backfilling
self-play loop because that loop discards intermediate rewards and contiguous
episodes. It composes the environment wrapper, search, Flashbax primitive,
opening enumeration and checkpoint path encoding instead. No production
MCTS/core/model behavior was edited.

## 2026-09-05: correctness and smoke

Eight initial focused CPU tests passed. The first checkpoint attempt exposed
empty optimizer-node loss and Flashbax dataclass serialization problems; fixed
in the MuZero format. The repeated CPU cycle and checkpoint load succeeded.
The sandbox TPU attempt could not access instance metadata; only that session's
process was stopped, with no lock removal. The unrestricted four-device TPU
smoke passed: 64 games, 876 real transitions, four updates, checkpoint saved.

## Experiment 1: Hex 4 vector baseline, seeds 0/1/2

Question: does self-play train predictions useful for real play, and does
learned two-rung search improve over the same policy network?

Change: train from random initialization for 300 cycles per seed. Fixed:
width 128, two residual blocks per tower, unroll 5, 16+8 expansions, batch 256,
16 updates per cycle, AdamW at 1e-3, replay 16 batches, and exploration for
the first eight moves. Only the seed varies. Checkpoints and evaluation occur
every 50 cycles, preserving regressions rather than choosing a favorite snapshot.

Evaluation: all legal two-ply openings, both colors, policy and search versus
random and against each other. Save raw actions, rewards, completion flags and
openings. This is limited opening coverage, not a proof of optimal play.
Prediction diagnostics use disjoint episodes generated by the initial self-play
policy, at unroll lengths 1/3/5/10; these reflect returns under that behavior
policy, not exact optimal values. Search/policy comparison matches parameters
and checkpoint; inference expansions and time differ. AlphaZero comparisons
will be reference-strength comparisons unless resource matching is established.

Decision: proceed to Hex 5 only with convincing learning and search benefit.
If predicted improvements do not translate to stronger real play, preserve
that failure and diagnose the model before increasing board size.

## Experiment 2: duration control, Hex 4 seed 0

The 300-cycle runs learn to beat random play but show inconsistent search
benefit. Seed 0 scores only 9.8% policy / 15.0% search against the existing
AlphaZero Hex 4 checkpoint in a CPU real-game evaluation (480 games each).
This is an unmatched reference: the checkpoint's training budget is unknown,
and its architecture and training data are not controlled against MuZero.
CPU timing is not compared to TPU timing.

Question: is the initial baseline simply undertrained after 4,800 updates?
Change only training duration to 3,000 cycles / 48,000 updates, from the same
seed-0 initialization and unchanged hyperparameters. Monitoring/checkpoint
frequency becomes 300 cycles; these use separate keys and do not affect
training. New diagnostics separate real-state error from absorbing padding
and report predicted positive rewards. Fixed: vector architecture, batch,
optimizer, replay, exploration, unroll, and search. No search redesign.

Decision: if duration improves real search strength and model diagnostics,
replicate across seeds before expanding boards. If it fails, inspect model
capacity and spatial inductive bias with a separate controlled experiment.

## User-directed alignment with production defaults

The initial pilot configurations were too small to represent production
AlphaZero defaults. They remain explicitly labeled `defaults = "pilot_v1"`.
New runs use `defaults = "alphazero"`, dynamically resolving applicable fields
from `CONFIG_FACTORIES`: batch sizes (except Hex 5 train batch 4096), learning
rate, warmup updates, weight decay and kernel-only mask, width/depth knobs,
search rungs/temperature/Q transform, exploration cutoff distribution,
optimizer updates per cycle, training budget, and monitoring cadence.
This is a user-directed baseline correction, not a single-variable ablation.

Hex 4 resolves to self-play/train batch 1024, LR 0.001, warmup 2036 updates,
width 64, depth 4, root temperature 1.3, 16+8 expansions, 10 updates per cycle
and 500 cycles. The width/depth settings still describe MuZero MLP towers,
not AlphaZero's convolutional trunk; parameter counts are not matched.
Replay uses approximately the production position capacity rounded to whole
fixed-length episode batches (125 batches × 1024 games × 16 allocated plies).
Actual stored positions are fewer because completed episodes are padded.

Remaining structural differences: each MuZero cycle collects complete episode
batches rather than ten incremental self-play steps, so experience/cycle differs;
there are recurrent reward losses and K=5 unrolls; and the model consists of
three learned components. Report experience, updates and accelerator time
explicitly rather than implying these are matched by shared defaults.

## User-directed production evaluation integration

Reuse `HexTrainingEvaluator` and `MoHexPool`, with the engine bank started
before JAX as in the production CLI. A new monitoring configuration runs both
policy-only and learned-search matches every 50 cycles. It preserves the
production all-first-moves, model-as-P1 design and raw move histories. The
bundled uncapped parallel-solver engine configuration is unchanged.

Also compose the production `_run_hex_diagnostics` initial-value grid through
a MuZero inference adapter, and record its opening-value MSE/sign accuracy.
Add production-style parameter/update norms, current LR, target sign counts,
episode-length statistics and truncation rate. These diagnostics never enter
training targets or latent search.

The user identifies the existing AlphaZero Hex 4 checkpoint as essentially
perfect play. Earlier forced-opening match percentages must be understood in
that context: forced openings may place either side in a theoretically lost
position. They are not unconstrained wins over a perfect opponent. MoHex's
all-first-move test instead reports how many known P1-winning openings the
model converts. Its inherited `perfect_play_achieved` field only denotes
opening-suite coverage; MuZero's W&B metric is named
`all_known_winning_openings_won` to avoid a broader claim.

## Experiment 3: production spatial model components

The 48,000-update vector pilot converts all four known Hex 4 winning openings
against MoHex in both modes. However, the 5,000-update vector baseline using
production defaults is weak: seed 2 converts one with search and zero with
policy-only play. Positive terminal-reward predictions remain low. Duration
helps, but a vector bottleneck discards the board's useful spatial structure.

Question: can the production convolutional representation make MuZero learn
useful dynamics faster at the production training settings?

Change: replace vector towers with a spatial latent architecture composed from
the existing `KataGoTrunk`, game-specific policy heads and `ValueHead` modules.
Representation and dynamics each use the production width/depth preset;
prediction uses the production heads without another trunk. State/action
concatenation uses explicit action planes (cell, column, pass or chess
from-square/move-plane encoding). This encodes actions, not future legality.
There is no observation reconstruction or latent consistency loss.

Fixed: inherited batch/LR/warmup/weight-decay settings, replay capacity,
exploration, 5-step training unroll, two-rung search, reward/value regression
objectives and evaluation cadence. This is an architecture comparison, not a
parameter-count match. The reused value/reward heads produce three logits
converted to a bounded scalar; the existing scalar MSE objective is retained.
The convolutional architecture uses production Mish and RVGL settings and
kernel-only decay includes RVGL branch kernels. Metadata records all choices.

Gates: two CPU tests check all-component gradients, action coordinate encoding
(including the inverse chess policy rotation), root masking and latent search.
Then a real four-device self-play/replay/update/checkpoint/MoHex smoke precedes
the long run. Progress to more seeds and Hex 5 only if real-play evidence
improves; retain failures and do not infer broad optimality from four openings.
# Hex5 staged self-play validation — 2026-09-05

Question: after the buffer audit and successful four-device full-size smoke,
does the spatial MuZero baseline learn stronger Hex5 play from self-play using
production's once-only position consume/drain convention?

Change: advance to Hex5 with the explicitly requested staged position pipeline.
This is a first learning validation, not a controlled attribution of gains to
board size or replay changes. Previous Hex4 episode-pipeline results remain
separate. No claim that the two pipelines are strength-equivalent is made.

Fixed: original AlphaZero Hex5 b4c128 spatial preset for each MuZero trunk,
self-play batch 1024, train batch 4096, LR 0.0001, kernel decay 0.0001,
20 updates per cycle, 1700 cycles, warmup schedule, 16+8 two-rung search,
MuZero unroll 5, and self-play-only training targets. Replay capacity is
2,048,000 consumed starting positions; its unroll payload uses more bytes
than AZ. Replay priming uses 82 complete-episode collection batches with
frozen parameters, derived from the 2045 AZ warmup steps and 25-ply cap.

Decision criteria: retain every periodic result, compare search and policy
against MoHex and each other, track current-policy held-out predictions over
multiple unroll lengths, and require zero malformed/overwritten fresh records.
Better predicted values without better real decisions trigger model/replay
diagnosis before any larger board. An apparent gain from one seed is provisional.
The smoke's 0/13 winning-opening conversions in both modes is the untrained
reference, not a failure of a learned checkpoint.

Diagnostics: numeric W&B tables and dynamic Plotly charts, no image uploads.
The original chart schema and behavior were located in the sibling AZ repository
and adapted with an equivalence test; see METRICS.md for provenance.
